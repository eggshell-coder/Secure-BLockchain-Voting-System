# Threat model

## Assets

- Voter identity and eligibility records
- Anonymous credential secrets
- Encrypted ballot contents and trustee decryption shares
- Frozen election manifest and accepted-ballot record
- Availability of voter, relayer, and verification services

## Adversaries considered

- A voter attempting to submit more than one ballot or an invalid ballot
- A malicious or compromised voter browser
- A registrar or administrator acting alone or colluding with another role
- A relayer that delays, observes, or drops submissions
- An attacker who reads or alters the off-chain voter registry
- A trustee quorum attempting to reveal individual choices
- A public observer correlating on-chain timing and metadata

## Required protections

- Keep personal data and plaintext choices off-chain and out of events.
- Separate eligibility authentication from ballot submission.
- Bind every proof to the election scope and frozen manifest.
- Use unique election-scoped nullifiers and reject duplicates.
- Freeze the voter group root, election dates, manifest, and verifier version.
- Publish enough encrypted artifacts and proof data for independent verification.
- Require a publicly verifiable tally proof before showing final results.
- Bind every aggregate decryption share to the candidate aggregate ciphertext and publish the share proof.
- Record administrator actions in a tamper-evident chain without voter PII.

## Explicitly unmitigated in this prototype

- Voter identity data resides in Supabase Postgres. The Node server uses a privileged server-only key; compromise of that key exposes the registry and must be treated as a high-impact incident. This build is for fictional data only.
- The administrator account is single-factor and configured through environment variables; there is no production identity provider or multi-role authorization.
- A university email domain shows control of a university mailbox, not active enrollment. The registrar must compare the claimed student ID against an authoritative roster.
- The registration server sees a verified user ID and Semaphore commitment together briefly during enrollment. The migration removes timestamp and legacy direct mapping columns and shuffles group order, but this is not blind credential issuance; server compromise/request tracing and old backups remain risks.
- The Solidity ballot box trusts one EIP-712 verification authority. A compromised authority can censor ballots or sign an invalid acceptance; the contract itself does not verify Semaphore or Ristretto proofs.
- The current 2-of-3 shares are split from a key originally generated by one administrator. That administrator retains the full secret, so this is demonstration math rather than threshold custody.
- The database SHA-256 chain and contract's Keccak ballot chain are separate commitments. There is no deployed inclusion proof tying their heads together, and no concrete `ITallyProofVerifier` contract.
- Malware or malicious extensions on the voter's device
- Coercion, vote buying, or observation of a remote voter
- Registrar collusion or an incorrect source roster
- Collusion by enough decryption trustees
- Network censorship, chain congestion, or broad service outages
- Removal of the newest rows from the audit chain without an independently retained head checkpoint

## Trust boundaries

The registrar learns voter identity and can presently correlate identity enrollment with the public commitment. The ballot client sees the selection before encryption. Trustees can potentially decrypt ballots if their threshold colludes. The attestation authority controls which server-verified ballots reach the current contract. The relayer sees network metadata even when it does not receive the voter ID. These assumptions must be documented and tested rather than described as trustless.

The browser uses the Supabase publishable key for Auth; row-level security and server-side authorization remain the security boundary. The Node API uses a privileged secret key for database access and owns the administrator session boundary; that key bypasses row-level security, so it must remain server-only, be rotated after exposure, and be restricted to a trusted deployment environment.
